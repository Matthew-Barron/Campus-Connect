# Campus Connect — Supabase / PostgreSQL

Campus Connect is a verified-student platform for marketplace listings, events, polls, societies, tutoring and notifications.

This version is migrated from MySQL to **Supabase PostgreSQL + Supabase Auth**.

## Architecture

- **Authentication:** Supabase Auth (`auth.users`)
- **Application profile:** `public.profiles`, linked 1:1 to `auth.users.id`
- **Database:** PostgreSQL on Supabase
- **IDs:** UUIDs generated by PostgreSQL
- **Authorization:** PostgreSQL Row Level Security (RLS) plus backend ownership checks
- **Backend:** Express + `@supabase/supabase-js`
- **Frontend:** Existing REST UI with Supabase Auth session persistence and token refresh

The backend never stores application passwords, password hashes, reset tokens, or custom JWT secrets.

## 1. Create the Supabase project

Create a project in Supabase and copy:

- Project URL
- Publishable/anon key
- Service-role key (server only)

## 2. Configure Supabase Auth

For the current campus-only registration flow:

- Keep email/password authentication enabled.
- Set the site URL to your deployed frontend URL.
- Add the local and production password reset URLs under **Authentication → URL Configuration → Redirect URLs**.
- If you want registration to log the user in immediately, disable email confirmation. If confirmation remains enabled, the application will ask the user to confirm their email before login.

The required CPUT student email format is still `@mycput.ac.za`.

## 3. Create the database

Open the Supabase SQL Editor and run:

```text
DATABASE_SCHEMA.sql
```

`DATABASE_SCHEMA_HOSTED.sql` contains the same PostgreSQL/Supabase schema for deployments that prefer the hosted-schema filename.

Do **not** run the old MySQL schema against Supabase.

The schema creates:

- `profiles`
- `listings`
- `listing_responses`
- `events`
- `event_rsvps`
- `polls`
- `poll_votes`
- `societies`
- `society_members`
- `tutoring_listings`
- `notifications`
- reporting views
- indexes
- `updated_at` triggers
- RLS policies
- the `auth.users → profiles` trigger

## 4. Configure the backend

Copy `.env.example` to `.env` and fill in:

```env
SUPABASE_URL=https://YOUR_PROJECT_REF.supabase.co
SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY=YOUR_SUPABASE_SERVICE_ROLE_KEY
PORT=5000
NODE_ENV=development
FRONTEND_URL=http://localhost:5000
PASSWORD_RESET_REDIRECT_URL=http://localhost:5000/
```

**Never expose `SUPABASE_SERVICE_ROLE_KEY` to the browser.**

## 5. Install and run

Because dependencies are defined in `package.json`, run:

```bash
npm install
npm run dev
```

Production:

```bash
npm start
```

## Authentication flow

```text
Browser
  ↓
Supabase Auth
  ↓
Supabase access/refresh session
  ↓
Authorization: Bearer <access token>
  ↓
Express
  ↓
Supabase Auth getUser()
  ↓
PostgreSQL / RLS
```

The browser session is persisted and refreshed by the Supabase client. The old custom `localStorage.token`, `JWT_SECRET`, `bcrypt` password storage, and custom reset-token database fields have been removed.

## Password reset

Password reset is handled by Supabase Auth. The reset email returns to the configured application URL, where the Supabase recovery session allows the user to set a new password.

## API compatibility

The existing API routes remain available, including:

- `/auth/register`
- `/auth/login`
- `/auth/forgot-password`
- `/auth/reset-password`
- `/auth/me`
- `/listings`
- `/events`
- `/polls`
- `/societies`
- `/tutoring`
- `/notifications`
- `/health`

Application IDs are now UUIDs even though the API field names such as `user_id`, `listing_id`, and `event_id` are retained for frontend compatibility.

## Security notes

- RLS is enabled on all application tables.
- Public reads are limited to intentionally public resources.
- User-owned writes require `auth.uid()` ownership.
- Notifications are private to their recipient.
- The service-role client is used only for trusted server-side operations such as system-generated notifications and profile provisioning.
- Do not put the service-role key in `public/`, frontend JavaScript, `.env.example`, or source control.

## Migration note

The old MySQL-specific constructs have been removed:

- `AUTO_INCREMENT`
- MySQL `ENUM`
- `DATETIME`
- `ON UPDATE CURRENT_TIMESTAMP`
- `INSERT IGNORE`
- `ON DUPLICATE KEY UPDATE`
- `DATE_SUB`
- `mysql2`
- custom JWT signing
- application password hashes
- custom password-reset tokens

They are replaced with PostgreSQL UUIDs, PostgreSQL enum types, `timestamptz`, triggers, `ON CONFLICT`/Supabase upserts, Supabase Auth, JSONB, and RLS.

## Supabase CLI workflow

The project also includes:

```text
supabase/config.toml
supabase/migrations/20261007143000_initial_schema.sql
```

If you use the Supabase CLI, link the project and push the migration instead of pasting the schema manually:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

For local development:

```bash
supabase start
supabase db reset
```


## Blank-screen fix

The browser Supabase client is bundled locally at `public/vendor/supabase.js` instead of being loaded from jsDelivr. The frontend also renders the login screen before asynchronous configuration/session initialization, so a slow or unavailable backend no longer results in an apparently blank page.

## Email behavior

This application currently sends authentication emails through Supabase Auth (account confirmation/password reset). Listing messages are stored as in-app notifications and do not currently send outbound email.

There is no email address belonging to ChatGPT that the application can send to. If you want application messages/test emails delivered to a specific inbox, configure an email provider (SMTP/Resend/etc.) and a real recipient address; do not put provider secrets in `public/` or frontend JavaScript.
